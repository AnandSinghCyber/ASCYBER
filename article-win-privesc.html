Advanced Windows Privilege Escalation

By Anand Singh August 20, 2026 7 min read

You've successfully gained a foothold on a Windows machine. You execute whoami and see that you are a low-privileged user. To fully compromise the Active Directory environment or dump credentials, you need NT AUTHORITY\SYSTEM. This is where Privilege Escalation (PrivEsc) comes in.

The Mindset of PrivEsc

Privilege escalation is rarely about finding a zero-day exploit (though kernel exploits like PrintNightmare certainly exist). More often than not, it's about finding misconfigurations—flaws in how administrators have set up services, permissions, and third-party software.

Let's dive into three classic Windows PrivEsc vectors that every Red Teamer and Pentester must know.

1. Unquoted Service Paths

When a Windows service is installed, its executable path is written to the registry. If this path contains spaces and is not enclosed in quotes, Windows has to guess where the executable actually lives.

# Example of an Unquoted Service Path:
C:\Program Files\Some Enterprise Software\service.exe

Because there are spaces, Windows will attempt to execute files in the following order before finally reaching service.exe:

  1. C:\Program.exe
  2. C:\Program Files\Some.exe
  3. C:\Program Files\Some Enterprise.exe
  4. C:\Program Files\Some Enterprise Software\service.exe

The Exploit: If a low-privileged user has write permissions to the C:\Program Files\ directory, they can drop a malicious payload named Some.exe. The next time the service restarts, Windows will execute the malicious payload with the privileges of the service (often SYSTEM) instead of the actual service executable.

2. Insecure Service Executables

Sometimes, the vulnerability isn't the path, but the executable itself. If the permissions on a service executable (e.g., C:\App\service.exe) allow low-privileged users to modify or overwrite the file, you have a direct path to SYSTEM.

# Check permissions using icacls or accesschk (Sysinternals)
accesschk.exe -quvw "Everyone" C:\App\service.exe

# If you see "FILE_ALL_ACCESS", you can overwrite it:
move C:\App\service.exe C:\App\service.bak
copy payload.exe C:\App\service.exe
net stop AppService
net start AppService

3. DLL Hijacking

When a Windows application starts, it searches for required Dynamic Link Libraries (DLLs) in a specific order (the DLL Search Order). If it attempts to load a DLL that doesn't exist, or if it searches a directory where a low-privileged user has write access before finding the actual DLL, an attacker can perform DLL Hijacking.

The Exploit: By crafting a malicious DLL with the exact name the application is looking for, and placing it in a higher-priority directory (like the application's current working directory, if permissions allow), the application will load the malicious DLL instead of the legitimate one.

Conclusion

Automated tools like WinPEAS and Seatbelt are fantastic for enumerating these misconfigurations rapidly. However, understanding the underlying mechanics of why these vulnerabilities exist is crucial for manual verification and for bypassing endpoint detection and response (EDR) solutions that might flag automated tools.
